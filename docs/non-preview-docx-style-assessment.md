# 非 Preview DOCX 导出格式评估

评估日期：2026-05-17

## 评估范围

本评估只覆盖 `md-viewer-docx-service` 支持的四种非 `preview` DOCX 导出格式。以下名称是当前 API/style 枚举，不等同于建议的对外展示文案：

- `standard`：通用文档
- `official`：正式公文
- `internal`：机关内部文件
- `report`：调研/分析报告

`preview` 格式不在本轮重点范围内。本文目标不是确认功能“能否导出”，而是评估这四种格式是否足以作为稳定、可解释、可交付的 Word 样式预设；除非后续另行设计模板系统，否则不应把它们宣传为完整行业模板。

## 当前结论

现实结论：**P0/P1 基础项已实施，仍不应宣传为完整模板**

四种格式当前都能生成可打开的 DOCX，基础结构测试也能通过；本轮已实施命名降级、默认页脚、字体状态 warning、H5/H6、基础嵌套列表、表格内图片注入、多字体嵌入和表头跨页重复。但如果按“用户下载后可直接作为对应场景正式文档使用”的标准看，仍有差距。主要风险转移到中文字体授权与跨端显示、复杂 Markdown 兼容、完整模板能力和视觉验收证据。

其中 `official` 仍是最高风险样式。代码与 README 已将其降级为“公文正文样式”，但用户仍可能期待接近 GB/T 9704 及机关公文习惯的完整模板；当前实现仍更接近“公文正文排版近似”。

本文件当前定位应是发布决策稿，而不只是问题清单。P0/P1 中可由服务端落地的部分已完成；P2 已先落地 fixture 矩阵、结构门禁测试和发布验收清单，视觉基线、性能回归和 P3 完整模板系统仍需后续推进。

## 服务职责与发布边界

当前实现更接近 **Markdown 到 DOCX 的转换器 + 内置正文排版预设**，不是完整 DOCX 模板引擎。这个边界必须写入 README、接口文档和客户端文案。

| 项目 | 本轮应承诺 | 本轮不应承诺 |
|---|---|---|
| Markdown 内容 | 常用标题、段落、列表、表格、代码块、引用、图片的稳定转换 | 完整 CommonMark/GFM 语法全覆盖 |
| 样式预设 | 页面边距、字体名、字号、行距、标题层级、表格/图片基础样式 | 红头、版记、签发人、印章区、封面、目录、脚注等完整行业模板 |
| `reference.docx` | 作为有限参考文档打开，并允许部分页面/样式基础继承 | 完整继承 Word 模板、编号样式、页眉页脚、目录字段和所有主题样式 |
| 跨端效果 | 尽量生成 Word/WPS/LibreOffice 可打开文件，并提示降级风险 | 保证各系统字体和分页完全一致 |

如果产品目标升级为“正式公文模板”或“完整报告模板”，应另起模板系统设计：需要结构化字段、frontmatter、样式映射、模板占位符、页眉页脚、目录、页码和附件规则，不能只扩展当前 `presets.py` 参数。

## 对外命名、默认值与提示文案

建议 API 枚举可暂时保持兼容，但 UI 展示名和说明必须降级，避免用户把“样式预设”理解成“完整模板”。

| API style | 建议 UI 展示名 | 适合场景 | 明确不包含 | 默认页脚 |
|---|---|---|---|---|
| `standard` | 通用阅读文档 | 日常资料、技术说明、普通工作文档 | 正式中文排版模板 | 可保留或由客户端设置 |
| `official` | 公文正文样式 | 简单公文风格正文、三号仿宋近似排版 | 红头、发文字号、签发人、版记、印章区、单位模板合规保证 | 默认关闭 |
| `internal` | 内部材料正文样式 | 内部通知、汇报材料、工作说明 | 密级、编号、部门、固定页眉页脚、审批流模板 | 默认关闭 |
| `report` | 报告正文样式 | 调研/分析报告正文、图表说明 | 封面、摘要、目录、图表清单、参考文献格式 | 默认关闭 |

客户端导出时建议展示一句限制说明，例如：“该样式只调整正文排版，不保证符合单位模板；提交前请在 Word/WPS 中人工核对。”

## Warning 与错误反馈契约

服务端已经存在 warning header 的基础，但发布前需要把 warning 变成用户可见的产品反馈，而不是只停留在响应头。

| 类型 | 示例 | 客户端建议 |
|---|---|---|
| 信息 | `reference.docx` 已加载，但部分样式会被当前预设覆盖 | 导出完成详情中展示 |
| 警告 | 未检测到 `仿宋_GB2312`，实际显示取决于打开端字体替换 | 导出成功 toast 中提示，并提供详情 |
| 警告 | 部分图表渲染失败或占位符未替换 | 标记为“已导出但有内容降级” |
| 阻断 | full renderer 不可用且用户选择严格模式 | 阻止下载，给出重试或切换模式建议 |

调用方需要在 200 响应中读取 warning，并把 warning 写入导出结果详情或导出历史。否则用户会看到“导出成功”，但打开文件后才发现字体、图表或结构不符合预期。

## 字体离线存放与授权策略

可以支持字体离线存放，但必须区分“可随开源项目分发的字体”和“用户自行提供的授权字体”。开源项目不能因为使用开源协议，就再分发没有授权的商业字体或系统字体。

### 不建议公开分发的字体

以下字体当前按未授权处理，不应放入 GitHub 仓库、Release 附件、Docker 镜像、公开 CDN 或自动下载脚本：

- `方正小标宋简体`
- `仿宋_GB2312`
- `宋体`
- `黑体`
- `微软雅黑`

原因：

- Windows 随附字体通常允许在已授权系统上使用，但不等于允许复制到服务器、镜像或应用包中再分发。
- 方正字体属于商业字库，必须按用途取得授权后才能随部署包或镜像分发。
- DOCX 字体嵌入也需要尊重字体自身的嵌入权限位，不能只因为技术上能写入 `word/fonts/` 就默认允许。

### 推荐的开源默认字体

开源版可以内置或随镜像打包授权清晰的开源 CJK 字体，用作离线 fallback：

| 用途 | 推荐字体 | 说明 |
|---|---|---|
| 通用无衬线 | Noto Sans CJK SC / Source Han Sans SC | 接近黑体/微软雅黑方向 |
| 通用衬线 | Noto Serif CJK SC / Source Han Serif SC | 接近宋体方向 |
| 等宽代码 | Sarasa Mono SC 或 Noto Sans Mono CJK | 用于代码块和等宽内容 |

这些字体不能完全替代 `方正小标宋简体`、`仿宋_GB2312` 的公文观感，因此 `official` 仍应显示“近似排版”或字体降级 warning。

### 私有部署离线字体包

对单位内部或私有化部署，建议支持用户自行放置已授权字体：

```text
fonts/
  open/
    NotoSansCJKsc-Regular.otf
    SourceHanSerifSC-Regular.otf
  private/
    FZXiaoBiaoSong.ttf
    FangSong_GB2312.ttf
    SimSun.ttc
    SimHei.ttf
```

加载方式：

```bash
MD_VIEWER_DOCX_FONT_DIRS=/app/fonts/private:/app/fonts/open
```

实现上应保证 `fonts/private/` 可被 `.gitignore` 排除，只提供 `README` 和示例文件名，不提交真实未授权字体。私有镜像或内网制品库可以按单位授权另行打包。

### 字体状态契约

建议 `/healthz` 或导出响应增加按 style 的字体状态，而不是只返回笼统的 `fontsAvailable`：

```json
{
  "official": {
    "方正小标宋简体": "missing",
    "仿宋_GB2312": "missing",
    "黑体": "fallback:Noto Sans CJK SC"
  },
  "report": {
    "宋体": "fallback:Noto Serif CJK SC",
    "黑体": "fallback:Noto Sans CJK SC"
  }
}
```

状态建议：

- `exact`：目标字体存在并可用。
- `fallback`：目标字体不存在，但存在明确替代字体。
- `missing`：目标字体和替代字体都不可用。
- `embeddable` / `not_embeddable`：字体文件是否允许嵌入 DOCX。

导出时，如果 `official/internal/report` 只使用 fallback 字体，应继续导出但返回 warning；如果用户选择严格模式，可以阻断导出并提示安装或挂载授权字体。

参考依据：

- Microsoft 字体再分发说明：<https://learn.microsoft.com/en-us/typography/fonts/font-faq>
- Noto 字体说明：<https://github.com/notofonts/noto-cjk>
- Source Han Sans / Source Han Serif：<https://github.com/adobe-fonts/source-han-sans>、<https://github.com/adobe-fonts/source-han-serif>

## 共性问题

### 1. Markdown 结构解析仍非完整 AST

本轮已支持 H1-H6，`official` 的 H5 可作为四级标题渲染为 `Heading5`，基础列表缩进层级也会进入 `Block.level`。这解决了 H5 退化正文和简单嵌套有序列表错序问题。

仍需注意：

- 当前解析器仍是正则逐行模型，不是完整 CommonMark/GFM AST。
- 复杂嵌套块、列表内表格、列表内多段落、任务列表等语法仍不应承诺完整支持。
- 对不支持语法需要继续通过 warning 或文档说明降低预期。

已覆盖样例：

```markdown
1. 第一条
   1. 子条目
2. 第二条
```

当前应渲染为：

```text
1. 第一条
   1. 子条目
2. 第二条
```

### 2. 字体依赖仍受授权与打开端影响

`official` 依赖：

- `方正小标宋简体`
- `仿宋_GB2312`
- `楷体_GB2312`
- `黑体`

`internal` / `report` 依赖：

- `黑体`
- `宋体`

`standard` 依赖：

- `微软雅黑`

仓库内置字体只有 `NotoSansCJKsc-Regular.otf`。本轮已增加 `/healthz.fontStatus`、导出阶段字体 fallback/missing warning、多字体嵌入和 `fonts/private/` 忽略规则。但如果部署环境没有目标字体，Word/WPS 仍可能自行替换，跨端显示仍不可完全保证。未授权字体不应随开源仓库或公开镜像分发，只能由用户自行放置或在私有部署中挂载。

风险：

- 公文标题无法呈现预期字体。
- 不同系统打开同一 DOCX 视觉差异大。
- 用户以为服务“按公文格式导出”，实际受本机字体影响很大。

### 3. 表格布局仍偏启发式

非 `preview` 表格使用固定或自适应宽度，并复用类似 preview 的列宽估算算法。

当前优点：

- 基础边框、表头背景、单元格边距已有契约测试。
- 表格行设置了 `cantSplit`，可减少单行跨页破碎。

风险：

- 长表格行不能跨页，可能造成上一页大面积空白。
- 已设置表头跨页重复。
- 宽表格、长英文/URL、长代码字段可能仍然挤压或溢出。
- 表格内如果出现图表占位符，图片注入器已能遍历表格单元格段落；更复杂容器仍需后续覆盖。

### 4. 图表和图片注入仍需覆盖复杂容器

`image_injector.py` 已从只遍历 `doc.paragraphs` 改为递归遍历文档和表格单元格段落。这对普通段落和表格单元格中的图表占位符有效，但对更复杂容器仍有风险：

- 引用块表格中的图表
- 复杂列表项内的图表
- 页眉页脚、文本框等 python-docx 不易遍历的容器

另外，`report` 对图表有最小宽度策略，能改善小图太小的问题，但也可能把部分不适合放大的图片放得过大。

### 5. 默认页脚策略已按样式区分

本轮已将 `official / internal / report` 的默认页脚改为关闭；`standard / preview` 仍默认保留“由 MD Viewer 生成”。调用方仍可显式传 `footerText` 覆盖默认行为。

### 6. 自定义 reference.docx 支持深度有限

`referenceDocxBase64` 当前主要验证 DOCX 可读并作为 `Document(reference_docx_path)` 打开，后续仍由代码重设页面尺寸、边距、段落和块样式。它不是完整的 Word 模板样式继承系统。

风险：

- 用户以为可通过 reference.docx 完整控制模板，实际只部分生效。
- 内部模板中的页眉、页脚、编号样式、正文样式、表格样式未必按预期复用。

### 7. 调用方与客户端契约仍需客户端落地

服务端可以通过 header 返回 warning，但文档还需要明确调用方责任：

- 客户端是否读取 200 响应中的 warning。
- warning 显示在导出 toast、导出历史还是详情弹窗。
- 用户能否区分“完全成功”和“成功但有降级”。
- 修改默认页脚或 UI 展示名是否会影响已有调用方。

如果调用方继续只展示“导出成功”，字体替换、图表缺失和 reference.docx 部分生效都会变成用户打开文件后才发现的问题。

### 8. 发布验收缺少量化门禁

现有样例和测试能证明基础结构，但还不能形成发布门禁。发布前需要定义：

- 哪些 Markdown 结构丢失属于阻断。
- 哪些 warning 可接受，哪些必须阻断导出。
- 每个样式至少通过哪些 fixture。
- Word/WPS/LibreOffice 抽检由谁执行，检查项是什么。
- PDF 截图或 PNG 快照如何作为回归基线。

## 分格式评估

### Standard

当前可用性：较高。

适用场景：

- 普通工作文档
- 技术说明
- 日常资料整理

主要问题：

- 字体使用 `微软雅黑`，Linux/Docker 默认环境不一定真实存在。
- 正文无首行缩进，符合通用文档可以接受，但不适合偏正式中文文档。
- H1-H6 和基础嵌套列表已支持，但复杂列表内块级内容仍不承诺完整兼容。
- 表格和代码块可用；复杂宽表格、长 URL、长英文仍需视觉验收。

建议：

- 明确 `standard` 是“通用阅读版”，不是正式中文排版模板。
- 继续补强字体回退说明：`微软雅黑 -> Noto Sans CJK SC / Source Han Sans SC -> 系统可用中文字体`。
- 将宽表格、长 URL、中英混排加入后续 fixture。

### Official

当前可用性：基础可用，但不应宣传为完整正式公文模板。

适用场景：

- 简单公文风格正文
- 需要三号仿宋、固定行距、公文边距的近似排版

主要问题：

- H5 已作为公文四级标题落地，但完整公文标题体系仍缺少结构化字段和模板约束。
- 依赖商业或系统字体，默认 Docker 镜像不具备完整字体条件。
- 没有红头、发文字号、签发人、主送机关、附件、成文日期、印章区、版记、页码等完整公文结构。
- 引用块被特殊处理为“注：”或普通段落，但复杂引用内结构仍有限。
- 默认页脚已关闭；调用方显式传入 `footerText` 时仍会覆盖默认行为。
- 基础嵌套有序列表已修复；复杂条款、列表内表格和多段落仍需后续 AST 化能力。

建议：

- 对外继续使用“公文正文样式”或“公文排版近似”，除非后续补齐完整结构。
- 增加公文专用 fixture：标题、主送机关、正文、附件、日期、版记、页码。
- 客户端读取并展示字体 warning，例如“未检测到仿宋_GB2312，实际显示取决于 Word/WPS 字体替换”。
- 不公开分发 `方正小标宋简体`、`仿宋_GB2312`，只支持用户自行挂载授权字体；开源版使用 Noto/思源近似。

### Internal

当前可用性：中等。

适用场景：

- 内部通知
- 内部汇报材料
- 机关内部工作说明

主要问题：

- 仍依赖宋体/黑体，不同环境下字体可能替换。
- H1-H6 和基础嵌套列表已支持，但复杂列表内块级内容仍不承诺完整兼容。
- 没有内部文件常见的密级、编号、部门、日期、页眉页脚等模板字段。
- 图表较多时，15pt 正文和 1.35 倍行距容易造成页数增长。

建议：

- 明确 `internal` 是“机关内部正文样式”，不是完整内部文件模板。
- 增加页眉/页脚与元信息字段的设计讨论。
- 增加长文档和图表密集型样例验收。

### Report

当前可用性：中等偏高。

适用场景：

- 调研报告
- 分析报告
- 普通数据说明文档

主要问题：

- `report` 会把部分来源宽度超过阈值的图表放大到至少 15cm，这对截图图表有利，但对普通图片可能过度放大。
- 基础嵌套列表已修复，但列表内表格、多段落、任务列表等复杂结构仍不承诺完整兼容。
- 表格跨页、长 URL、宽表格仍需视觉验收。
- 没有封面、摘要、目录、图表清单、参考来源格式等报告增强结构。

建议：

- 区分“图表截图”和“普通图片”的尺寸策略。
- 增加报告类样例：摘要、目录、图表、宽表格、参考来源。
- 增加图表尺寸的视觉验收阈值。

## 可用性评级标准

为了避免“可用”“中等”“较高”变成主观判断，建议后续评审统一使用以下评级：

| 评级 | 判定标准 | 发布含义 |
|---|---|---|
| 不可用 | DOCX 损坏、无法打开、核心内容缺失 | 阻断发布 |
| Demo 可用 | 文件可打开，但常用 Markdown 结构存在丢失或错序 | 只能内部验证 |
| 内部可用 | 常用结构基本正确，但字体、分页或复杂图表仍有 warning | 可灰度，必须显示限制说明 |
| 对外可用 | 结构、字体 warning、跨端抽检、视觉样例均有证据 | 可对外宣传为样式预设 |
| 模板可用 | 具备结构化字段、模板继承、页眉页脚、目录/页码等能力 | 才能宣传为完整模板 |

按该标准，当前四种非 `preview` 格式最多处于 Demo 可用到内部可用之间；`official` 不能按“模板可用”宣传。

验收方式应分三层：

1. 机读断言：生成四种 DOCX，解包检查 `word/document.xml`、`word/styles.xml`、表格、图片、标题层级、页脚和 warning。

## 修复优先级建议

### P0：发布前必须完成的契约修订

P0 不是继续追问“要不要做完整模板”，而是先把当前能力边界写清楚，并避免错误承诺。

| 事项 | 动作 | 验收标准 |
|---|---|---|
| 产品命名 | UI 将 `official/internal/report` 降级为“公文正文样式 / 内部材料正文样式 / 报告正文样式” | 客户端不再出现“完整模板”暗示 |
| 默认页脚 | `official/internal/report` 默认关闭“由 MD Viewer 生成” | 样例 DOCX 中不出现默认署名 |
| 调用方影响 | 列出当前调用四种 style 的客户端和接口路径 | 明确改名/默认值是否 breaking |
| warning 展示 | 200 响应中的 warning 在客户端可见 | 导出成功但有降级时用户能看到详情 |
| `reference.docx` 契约 | README/API 文档说明哪些会保留、哪些会被覆盖 | 用户不会误以为可完整控制模板 |
| 字体契约 | 明确开源默认字体、私有部署字体挂载、缺字 warning；不公开分发未授权字体 | 缺少目标字体时有可见提示，公开包中不包含商业/系统字体 |

## 待决策问题与影响面
